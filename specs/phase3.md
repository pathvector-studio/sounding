# 段 3：選別・ダイジェスト・Web UI・配信

> 状態: **承認済み**（2026-11-10、要判断はすべて (a)）。`docs/DESIGN.md` 2.2・3.4・4.1・4.3・6 章・7 章・9 章の段 3 を具体化する。前提は段 1（共有の層の原則、`specs/phase1.md`）と段 2（「現在地」の生成、`specs/phase2.md`）。

## 目的
取り込んで要約した会話と RSS 項目を、利用者の興味プロファイルで**選び、順位をつけ、1 日 1 回のダイジェストにまとめて届ける**。届いたダイジェストから Web UI に飛べば、会話の「現在地」の履歴と「なぜこれが載ったか」が読める。全部は見せない。

完了の目安（`docs/DESIGN.md` 9 章）：**自分の日次ダイジェストが届く**。

## 要件
- [x] R1: **会話の選別**。ダイジェストの期間（前回のダイジェストの終わりから今まで。初回は 24 時間）に人間の新着があった IETF の会話を候補にする。
  - 追跡中の WG のリストか、追跡中の draft 名を件名か本文に含む会話は、ルールで対象にする。
  - `extra_lists` の会話は、draft 名か `keywords.include` を含むときだけ対象にする。
  - `keywords.exclude` に当たる会話は外す。ただし追跡中の draft 名を含むものは外さない。
  - 対象の中で点数をつけ、上位 `profile.digest.max_threads` 件を載せる。点数に使うのは、新着の数、参加者の数、キーワードの一致数、「現在地」の変化（論点の状態が変わった数）。
- [x] R2: **RSS 項目の選別**。期間内に取得した有効なフィードの項目を候補にする。
  - `keywords.include` に当たる項目は対象にし、点数は一致数×フィードの `weight`。`keywords.exclude` に当たる項目は外す。
  - どちらにも当たらない項目の扱いは、決定事項 1 による。
  - 上位 `profile.digest.max_items` 件を載せる。
- [x] R3: **選別の理由を記録する**（`docs/DESIGN.md` 2.2）。候補ごとに、載ったか、点数、理由（どのルール・どのキーワード・LLM の判定と一言の理由）、判定したもの（ルールか LLM か）を残す。理由は Web UI に出す。
- [x] R4: **RSS 項目の要約**。載る項目だけを cheap 段で 1〜2 文に要約し、項目と言語ごとに保存する（共有の層）。入力はタイトルと前処理した本文で、段 2 と同じく信頼しないデータとして区切る。LLM が `none`、予算超過、失敗のときは要約なしでタイトルとリンクだけを載せる。
- [x] R5: **ダイジェストの生成**。worker が `profile.digest.schedule`（既定 07:00 TZ）に 1 回作り、本文を DB に残す。構成は次のとおり。
  - **健康状態**（問題があるときだけ）：期間内に失敗したジョブ、予算超過で要約しなかった会話の数、LLM が無効なこと。
  - **動きがあった会話**（点数の高い順）：件名、`status_line`、`changed_since_last`、新着の数、Web UI の会話ページへのリンク、最新メッセージのアーカイブへのリンク。「現在地」がない会話（LLM が `none`・予算超過・失敗）は件名と新着の数だけを載せる。
  - **手続きの更新**：期間内の `events`（I-D Action、WG 採択の呼びかけ、Last Call、公開など）のうち、追跡中の WG か draft のもの。
  - **関連記事**：RSS 項目のタイトル、要約、リンク。
  - 同じ期間を作り直しても 2 つできない。載せるものが何もない日も、「動きなし」のダイジェストを作る（届かないのが故障か静かな日かを区別できるように）。
- [x] R6: **Web UI**（サーバーサイドで描画する読み取り専用の画面）。
  - 最新のダイジェスト、過去のダイジェストの一覧と各回。
  - 会話のページ：「現在地」の最新版、版の履歴（各版の `changed_since_last`）、出典のリンク、選別の理由。
  - 状態のページ：ジョブごとの最後の成功時刻と直近の失敗、情報源ごとの取得状況、LLM の当日費用と予算、Atom フィードの URL。
  - 表示の言語は `profile.language`（ja と en）。
  - 本文は表示しない。要約と出典リンクだけ（`docs/DESIGN.md` 7 章）。
- [x] R7: **API**。R6 の画面と同じ内容を JSON で返す読み取り専用の API を、画面より先に作る（`specs/phase1.md` の原則 4）。画面は API と同じ問い合わせの関数を使う。
- [x] R8: **ログイン**。
  - `WEB_PASSWORD_HASH` が設定されていれば、画面と API はログインしないと見られない。
  - パスワードのハッシュを作る CLI（`hash-password`）を足す。
  - セッションは `SESSION_SECRET` で署名した Cookie にする（HttpOnly、SameSite=Lax、`PUBLIC_BASE_URL` が https なら Secure）。
  - 失敗が続いたら応答を遅らせる。
  - `SESSION_SECRET` が 32 バイト未満か `change-me` のままなら、web は起動しない。
  - `WEB_PASSWORD_HASH` が空のときの扱いは、決定事項 2 による。
- [x] R9: **Atom フィード**。ダイジェストを 1 回 1 エントリにして配る。
  - 中身は要約とリンクだけにする。
  - フィードリーダーはログインできないので、URL に推測できないトークンを入れる。トークンは `SESSION_SECRET` から導き、新しい秘密は増やさない。トークンが違えば 404 を返す。
  - URL は状態のページに出す。
- [x] R10: **配信**。`DELIVERY_CHANNELS` で有効にしたチャネルに、ダイジェストを作ったあと送る。
  - **email**：SMTP（587 は STARTTLS、465 は TLS）で `DIGEST_TO` に送る。プレーンテキストと HTML の両方を入れる。
  - **webhook**：Discord と Slack に互換の JSON で送る。長さの上限に合わせて切り詰め、Web UI へのリンクを付ける。
  - チャネルごとに成否を記録する。失敗したチャネルは次の実行で 1 回だけ再送する。送れたチャネルには二度送らない。
  - 秘密（SMTP のパスワード、webhook の URL）はログ・DB・エラーに出さない。
- [x] R11: **CLI と worker**。
  - CLI：`digest --once`（選別から配信まで）、`digest --once --no-deliver`、`show-digest [ID]`。
  - worker：`digest` ジョブを足す（advisory lock、`job_runs`）。
  - compose：web を既定で起動する（`profiles: ["web"]` を外す）。web には LLM のキー・`IDENTITY_SECRET`・SMTP と webhook の秘密を渡さない。
  - `status` に最後のダイジェストを出す。

## スコープ外
- **文書（draft）単位の束ね**（`docs/DESIGN.md` 3.4 の「動きがあった文書」）。段 3 は会話単位で並べる。束ねは拡張 1（Datatracker）と一緒に行う。
- Web UI からのプロファイル編集、マルチユーザー（`profiles` テーブルと `user_id`）。プロファイルは引き続き `config/profile.yaml`。利用者の層のテーブル（`selections`・`digests`・配信の記録）はこの段で作るが、利用者の列は持たない。マルチユーザーにするときに足す。
- 即時通知（会話が動いたらすぐ送る）、ジョブ失敗時の個別のアラート。失敗はダイジェストの健康状態の節と状態のページで知らせる。
- ダイジェストの公開（ログインなしで誰でも見られる URL）。
- 既読の管理、「興味なし」のフィードバック、検索。
- install.sh、公開モード 3 種の手順、バックアップは段 4。
- 評価セット、バッチ API（段 2 と同じく第二弾）。

## 受け入れ基準
1. `uv run pytest`（実 DB）がすべて通る。CI は偽の LLM プロバイダと、テスト内の偽の SMTP・webhook の受け手だけを使い、外部には接続しない。
2. `LLM_PROVIDER=none` で、段 1 で取得済みの sidrops と APNIC に対して `digest --once --no-deliver` を実行すると、外部への送信なしでダイジェストができる。会話は件名と新着の数、RSS はタイトルとリンクで載り、健康状態に「LLM が無効」と出る。
3. 段 2 と同じローカル LLM（Ollama の OpenAI 互換エンドポイント）で `digest --once --no-deliver` を実行すると、会話に `status_line` と `changed_since_last`、RSS 項目に要約が付く。選別の理由（ルール・キーワード・LLM の判定）が記録され、`show-digest` と Web UI で読める。同じ期間で作り直してもダイジェストは 1 つのまま。
4. `docker compose up -d` で web が起動し、ブラウザで最新のダイジェスト、会話のページ（版の履歴と出典）、状態のページが開ける。`WEB_PASSWORD_HASH` を設定すると、ログインしないと画面にも API にも入れず、違うパスワードでは入れない。
5. Atom フィードを feedparser で読むとエントリが取れ、トークンが違えば 404 になる。
6. 決定事項 3 のチャネルで、利用者のダイジェストが実際に届く。もう一度実行しても二度は届かない。送れないようにすると失敗が記録され、直したあとの実行で 1 回だけ届く。
7. ログ・DB・Web の応答に、SMTP のパスワード・webhook の URL・LLM のキー・メールアドレスが出ない（caplog と全テーブル検索のテスト）。web のコンテナの環境にこれらの秘密がない。

## 決めたこと
- **依存の追加**（承認事項）：`fastapi`（MIT）、`uvicorn`（BSD-3-Clause）、`jinja2`（BSD-3-Clause）。推移的に `starlette`（BSD-3-Clause）、`markupsafe`（BSD-3-Clause）、`h11`・`anyio`（MIT）、`click`（BSD-3-Clause）などが入る。どれも本番依存のライセンス条件を満たす。正確な一覧は実装の PR に `check-licenses.py` の結果として書く。足さないものは次のとおり。
  - パスワードのハッシュは標準ライブラリの `hashlib.scrypt` にする。`argon2-cffi` は足さず、`.env.example` の「argon2」は書き換える。
  - セッションの署名は標準ライブラリの `hmac` で作る（`itsdangerous` は足さない）。
  - ログインのフォームは urlencoded だけなので、標準ライブラリで読む（`python-multipart` は足さない）。
  - メールは `smtplib` と `email`、webhook は既存の `httpx`、Atom は `xml.etree` で書く。
- **画面は JavaScript なし**のサーバーサイド描画にし、CSS だけで整える（ダークモード対応）。ビルドの工程を持ち込まない。
- **選別のあとに「現在地」を作るのではなく、作ったあとに選ぶ**。追跡中の WG のリストはルールで必ず対象になるので、段 2 の日次の要約（06:00）は対象の会話をすでに要約している。ダイジェスト（07:00）はその結果を読んで順位をつけるだけで、会話の要約のために LLM は呼ばない。LLM を呼ぶのは RSS の境界の判定（決定事項 1 が (a) のとき）と RSS 項目の要約だけで、どちらも cheap 段を使い、段 2 と同じ日次予算に数える。
- **点数の式は単純な重み付きの和**にして、各項の値を選別の理由に残す。重みはコードに直接書き、設定項目にしない。実データで順位がおかしければ、重みを直す PR を出す。
- **RSS の LLM 判定と要約の上限**は 1 回の実行で 50 件ずつにし、コードに直接書く。費用の上限は日次予算で守られるので、これは暴走止め。
- **期間の決め方**：前回のダイジェストの `period_end` から今まで。前回が失敗して作られなかった日の分は、次の回にまとめて入る（取りこぼさない）。
- **リンク**：Web UI へのリンクは `PUBLIC_BASE_URL` から作る。出典はメッセージのアーカイブ URL（段 1 の `items.url`）と記事の URL。
- **データモデル**：migration `0003`（前進のみ）で次を足す。
  - 共有の層：`item_summaries`（項目・言語・要約・モデル・LLM の呼び出し）。
  - 利用者の層：`digests`（期間・本文の JSON・作成時刻）、`selections`（ダイジェスト・対象の種類と ID・載ったか・点数・理由の JSON・判定したもの）、`deliveries`（ダイジェスト・チャネル・成否・試行回数・時刻・エラーの要約）。
  - ダイジェストの本文は要約とリンクだけなので、保持期間で消さない。
- **web の DB アクセス**は読み取りだけにする（書くのはログインの失敗回数のようなプロセス内の状態だけで、DB には書かない）。読み取り専用の DB ロールを分けるのは段 4 で検討する。

## 決定事項（2026-11-10、ユーザー承認。すべて (a)。依存の追加も承認）
1. **キーワードに当たらない RSS 項目**
   - (a) cheap 段の LLM に、プロファイル（WG・draft・キーワード）に合うかを「はい/いいえ＋一言の理由」で判定させる（`docs/DESIGN.md` 2.2 の「境界例だけ LLM 判定」）。APNIC の 1 日数件なら Haiku で 1 日 $0.01 未満。LLM が `none` なら載せない。
   - (b) 載せない（ルールだけ。LLM の費用はゼロだが、キーワードを書いていない良い記事を落とす）。
   - (c) 新しい順に `max_items` まで載せる（選別しない）。
2. **`WEB_PASSWORD_HASH` が空のとき**
   - (a) ログインなしで開く（`.env.example` の今の説明どおり。Tailscale や Cloudflare Access の内側で使う前提）。起動時のログと画面の上部に「ログインなし」と警告を出す。ポートは 127.0.0.1 にしか開かないので、そのままでは LAN からも見えない。
   - (b) 起動しない（必ずパスワードを設定させる。安全側だが、Access で守っている人にも二重のログインを強いる）。
3. **受け入れ基準 6（実際に届く）で使うチャネル**
   - (a) webhook（Discord か Slack）。利用者が `WEBHOOK_URL` を `~/.config/sounding/dev.env` に入れる。
   - (b) email。利用者が SMTP の設定を入れる。
   - (c) Atom フィードだけ。秘密は要らないが、「届く」の確認はフィードリーダーで読めることになる。

## 実装後の追記（2026-11-11）
- 4 つの PR（#17〜#20）で実装した。受け入れ基準 1〜5・7 は確認済み（2・3 は sidrops と APNIC の実データ、3 はローカル LLM）。
- **受け入れ基準 6 は一部だけ確認**：worker のコンテナから手元の webhook の受け手へ、失敗の記録 → 直したあとに 1 回だけ届く → 再実行で送らない、を確認した。利用者の Discord / Slack に実際に届くかは、利用者が `WEBHOOK_URL` を設定してから確かめる（STATUS の予定）。
- **再送の範囲**：失敗した配信の再送は、試行 2 回まで・ダイジェストの作成から 3 日以内に限った（`RETRY_WINDOW`）。数週間前のダイジェストが突然届かないようにするため。spec にはなかった判断。
- **受け入れ基準 2 の文言と決定事項 1 (a) のずれ**：`LLM_PROVIDER=none` のとき、キーワードに当たらない RSS 項目は決定事項 1 (a) のとおり載らない。基準 2 の「RSS はタイトルとリンクで載り」は、キーワードに当たった項目についての記述として読む。
- **境界の判定のプロンプトを `rss-select-v2` にした**：v1 は記事が IETF や WG の名前に触れていないと「合わない」とし、ローカルの 7B モデルで全件落ちた。v2 は WG が扱う技術の内容で判断させる。7B モデルは判定の理由の中で WG の名前を取り違えることがある（モデルの限界。Claude では未確認）。
