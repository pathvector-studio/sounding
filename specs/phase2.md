# 段 2：LLM 抽象化・前処理・「議論の現在地」の生成と差分更新

> 状態: **案（承認待ち）**（2026-11-08）。`docs/DESIGN.md` 3 章・4.2・5 章・6 章・9 章の段 2 を具体化する。前提は段 1 の実装（`specs/phase1.md`、共有の層の原則）と段 0 の測定（`docs/spike-phase0.md`）。

## 目的
取り込んだ IETF ML の会話（スレッド）ごとに、LLM で「議論の現在地」（何が争点か・合意はどこまで進んだか・何が未決着か・前回から何が動いたか）を作り、**新着があった会話だけを、前回の状態＋新着メッセージで差分更新**して DB に履歴として残す。費用は予算の上限で必ず止まり、キーを入れるまで何も外に送らない。

完了の目安（`docs/DESIGN.md` 9 章）：**1 つの会話の状態履歴が差分で更新される**。

## 要件
- [ ] R1: `LLM_PROVIDER=none`（既定）のとき、要約ジョブは何も外部に送らず、`job_runs` に `skipped`（理由 `llm_disabled`）を残す。
- [ ] R2: `LLM_PROVIDER=anthropic` と `openai` を `.env` の切り替えだけで使える。呼び出し側は段（`cheap` / `main`）だけを指定し、モデル名は `LLM_MODEL_CHEAP` / `LLM_MODEL_MAIN` で決まる。出力は JSON Schema で強制し、スキーマに合わない応答は 1 回だけ再試行、それでも駄目なら「要約失敗」として記録する（推測で埋めない）。
- [ ] R3: LLM に渡す前に本文を前処理する：引用（`>` 行と各言語の引用見出し以降の引用ブロック）・署名・定型フッター（Note Well 等）を除き、**行間返信の直前の引用だけは短く残す**。自動送信メールは本文を渡さず、`events` の事実（種類・draft 名・日時）としてだけ渡す。合成コーパスのテストで、段 0 の目視で見つかった誤り（行間返信の文脈が消える、Outlook 形式の見出しの下の返信が消える）が起きないことを確かめる。
- [ ] R4: 会話の「現在地」を `docs/DESIGN.md` 3.2 のスキーマ（`status_line`・`issues`（立場・発言者・根拠）・`agreed`・`open_questions`・`next`・`changed_since_last`・`sources`）で生成する。**合意・リーニングの判断には根拠メッセージが必須**で、根拠のない判定は保存前に `open` に落とす。`process_state` は常に `null`（Datatracker は拡張 1）。
- [ ] R5: 差分更新：新着の人間のメッセージがある会話だけを対象にし、前回の状態＋新着だけを渡して次の版を作る。新着がなければ LLM を呼ばない。**前回の状態より古いメッセージが後から加わった場合**（祖先の補完、会話の統合）は差分ではなく作り直す。長い会話の初回は時系列に分割して要約してから統合する。
- [ ] R6: 状態は版ごとに DB に残す（会話・版数・状態 JSON・`changed_since_last`・対象にしたメッセージ・プロンプト版数・モデル・言語・作成時刻）。共有の層の原則どおり利用者の列は持たない。出力言語はプロファイルの `profile.language` で、状態は言語ごとに持つ。
- [ ] R7: すべての LLM 呼び出しを記録する（用途・プロバイダ・モデル・段・入出力トークン・キャッシュ読み書きトークン・推定費用・成否・所要時間）。同じ入力（前回状態＋新着＋プロンプト版数＋モデル＋言語のハッシュ）の再実行は記録済みの結果を使い、再度課金しない。
- [ ] R8: 1 日（TZ の暦日）の推定費用が `LLM_DAILY_BUDGET_USD` に達したら、その日の残りの要約を止め、止めた会話を `job_runs` に「予算超過のため未要約」として残す（黙って落とさない）。費用は組み込みの単価表で計算し、単価表にないモデルは同じプロバイダの最も高い単価で見積もって警告する。`0` は無制限。
- [ ] R9: プロンプトインジェクション対策：本文は信頼しないデータとして区切って渡し、本文中の指示に従わないことをシステムプロンプトに明記する。LLM にツールを与えない。システムプロンプトとスキーマは固定の先頭部に置き、プロバイダのプロンプトキャッシュが効く並びにする。
- [ ] R10: worker に `summarize` ジョブを足す（advisory lock、`job_runs`、終了シグナルで会話の区切りまで待つ）。CLI に `summarize --once [--conversation ID]` と、会話の現在地を表示する `show <conversation>` を足す。`status` に LLM の当日費用を出す。
- [ ] R11: `LLM_API_KEY` は worker だけが受け取り、ログ・`job_runs`・`llm_calls`・エラーに出さない。LLM に渡す内容に送信者のメールアドレスを含めない（表示名だけ）。

## スコープ外
- 選別（キーワード・スコア・境界例の LLM 判定）、ダイジェスト、配信、Web UI は段 3。**RSS 項目の要約も段 3**（選別の後に、載せるものだけを要約するため）。
- 文書（draft）単位の束ね（`docs/DESIGN.md` 3.1）は段 3 以降。段 2 は会話単位だけ。
- Datatracker と `process_state` は拡張 1。
- バッチ API（50% 安い非同期実行）は使わない（第二弾。日次の量が増えたら検討）。
- 評価セット（決着済みスレッドの「正解の現在地」との比較）は第二弾の早い段階。段 2 では受け入れ基準の手動確認だけ。
- `OpenAICompatibleProvider`（Ollama 等）は作らない。`LLM_API_BASE` を OpenAI プロバイダの接続先として渡せるだけにする。
- `parked` の論点を畳む処理は、状態が実際に長くなってから（目安：論点 10 件超の会話が出てから）。

## 受け入れ基準
1. `uv run pytest`（実 DB）がすべて通る。CI では偽のプロバイダだけを使い、外部の LLM には接続しない。
2. `LLM_PROVIDER=none` で `python -m sounding summarize --once` → 外部への送信なし、`job_runs` に `skipped`（`llm_disabled`）。
3. 手元で利用者が `LLM_PROVIDER`・`LLM_API_KEY`・`LLM_MODEL_*` を設定し、段 1 で取得済みの sidrops（30 日分）に対して `summarize --once` → 動きのある会話に版 1 ができ、`show` で現在地が読める。全件の推定費用と所要時間を PR に書く。
4. 同じ会話に新着を 1 通足して（実際の新着、または取得済みメッセージを外して入れ直す）再実行 → 版 2 ができ、`changed_since_last` が新着の内容を指し、LLM への入力が前回状態＋新着だけであること（`llm_calls` の入力トークンが版 1 より小さい）。新着のない会話は呼ばれない。
5. 同じ入力で再実行 → 課金されない（記録済みの結果を使う）。
6. `LLM_DAILY_BUDGET_USD` を小さくして実行 → 途中で止まり、未要約の会話が `job_runs` に残る。
7. 合意判定に根拠のない応答（偽のプロバイダで再現）→ 保存された状態では `open` になっている。
8. ログ・DB に `LLM_API_KEY` とメールアドレスが出ない（caplog と全テーブル検索のテスト）。

## 決めたこと（案）
- **SDK を使う**（依存の追加、承認事項）：`anthropic`（MIT）と `openai`（Apache-2.0）。httpx で直接書くこともできるが、再試行・タイムアウト・型付きのエラー・構造化出力の仕様変更への追従を SDK に任せた方が保守が軽い。どちらも本番依存のライセンス条件を満たす。
- **既定のモデル**（`.env.example` の例を置き換える）：anthropic は main `claude-opus-5-5`（$4 / $20 / 100 万トークン）、cheap `claude-haiku-5-5`（$0.10 / $0.50）。段 2 では cheap 段は長い会話の分割要約にだけ使う。openai は既定を置かず、未設定なら設定エラーで止める（モデル名の変化が速く、古い既定を配るより明示させる方が安全）。
- **費用の見込み**：段 0 の見積もり（sidrops＋idr＋grow で main 入力 7 万・出力 1.5 万トークン/日）を Opus 5.5 の単価にすると約 $0.6/日。思考のトークンが出力に加わるので、既定の `LLM_DAILY_BUDGET_USD=1.00` は据え置き、受け入れ基準 3 の実測で見直す。思考の深さは `effort` を明示して固定する（Opus 5.5 は思考を切れず、既定は `medium`）。
- **要約の対象**：有効な `ietf_mail` ソースの会話のうち、人間のメッセージの新着があるもの。`extra_lists`（`ietf` のような全体リスト）は量が多いので、**件名か本文に追跡中の draft 名・`keywords.include` を含む会話だけ**を対象にする（選別の本体は段 3。ここでは費用を守るための最小の絞り込み）。
- **実行のタイミング**：`summarize` は**日次**（既定 06:00 TZ、取得の後・段 3 の配信の前）。毎時にすると 1 つの会話が 1 日に何度も差分更新され、状態 JSON（入力の 8 割）を毎回送ることになり費用が数倍になる。即時性は段 3 の要件で必要になったら見直す。手動は `summarize --once`。
- **言語**：状態は（会話, 言語）ごとに持つ。共有の層に利用者の列を入れずに、将来ほかの言語の利用者が増えたら言語ごとに 1 回ずつ作るだけで済む。
- **作り直しの判定**：状態は「対象にしたメッセージ」を持ち、新着の中に前回の最後のメッセージより古いものがあれば作り直す。祖先の補完と会話の統合はどちらもこの形で現れるので、別々に扱わない。
- **キャッシュ**：結果の再利用（R7）は `llm_calls` に入力ハッシュと応答を持たせて行う。別のキャッシュ表は作らない。本文は保持期間（既定 90 日）で消えるので、期間を過ぎた会話は作り直せない。これは仕様として README に書く。
- **拒否**（`stop_reason: refusal`）は要約失敗として記録し、自動で別モデルに切り替えない（利用者のモデル選択を勝手に変えない）。
- **データモデル**：migration `0002`（前進のみ）で `conversation_states` と `llm_calls` を足す。`docs/DESIGN.md` 8 章の `thread_states` は段 1 で `conversation_states` に改名済み。

## 要判断（承認時に選んでほしい点。推奨は (a)）
1. **SDK の追加**：(a) `anthropic` と `openai` の公式 SDK を足す ／ (b) 依存を増やさず httpx で直接書く。
2. **実行のタイミング**：(a) 日次 06:00 ／ (b) 取得のたび（毎時。現在地は新しいが費用が数倍）。
3. **既定の main モデル**：(a) `claude-opus-5-5` ／ (b) より安い `claude-sonnet-5-5`（$2 / $10。品質は受け入れ基準 3 で比べられる）。

## 実装計画（PR 単位。承認後、親が 1 項目ずつ subagent に渡して検証する）
1. **前処理**：合成コーパスと前処理（R3）。LLM なしで完結。
2. **LLM 抽象化と記録**：プロバイダ 2 つ、構造化出力と再試行、`llm_calls`・単価表・予算・結果の再利用（R2・R7・R8・R11）、migration `0002`、依存の追加。
3. **現在地の生成**：プロンプト、スキーマ、根拠の検査、初回の分割要約、差分更新と作り直し、`conversation_states`（R4〜R6・R9）。
4. **運用**：`summarize` ジョブと CLI（R1・R10）、`.env.example`、README、`AGENTS.md` 4.4、CHANGELOG。受け入れ基準 3〜6 を利用者のキーで手動確認して PR に書く。
